ATLAS — Full Project Guide

A GitOps pipeline for Morpheus / ACS. Written for someone who knows nothing about the project.

1. What is this project, in one paragraph?

Companies run lots of servers and cloud infrastructure using a management tool called Morpheus (also known as Atlas Cloud Services / ACS). Today they configure it by clicking buttons in a web dashboard. This project replaces that clicking with text files stored in Git, so every change is recorded, reviewed, reversible, and can be copied safely between environments (DEV → TEST → PROD). That approach is called GitOps: Git becomes the single source of truth for your infrastructure.

The single most important thing to know This project is mock-first by design. It ships with a fake Morpheus that runs on your laptop, so you can build, test, and demonstrate the entire system with no real credentials and no internet. You are never blocked waiting for API access.

2. The problem (told as a story)

Imagine a team managing hundreds of virtual machines through the Morpheus dashboard. One day:

  • "Who changed the web server config last week?" — Nobody knows. Someone clicked something. There is no history.
  • "That change broke production — can we undo it?" — No. Clicking a button has no "undo".
  • "TEST works perfectly. Copy it exactly to PRODUCTION." — Only by manually re-clicking every single setting by hand, hoping nobody fat-fingers a value.

So the real problems are: no history, no review, no rollback, no safe promotion between environments.

3. The solution: GitOps

Software developers solved exactly this problem for source code decades ago using Git — a system that records every change, who made it, when, and why, and lets you review changes before they apply and revert them afterwards. This project applies that same idea to infrastructure configuration.

The new way of working:

1. Edit a YAML text file        →  "I want a web server with these settings"
2. Open a Merge Request (MR)    →  a teammate reviews and approves it
3. The CI/CD pipeline runs      →  a robot automatically pushes it into Morpheus
What you gain Full history (Git log), peer review (Merge Requests), instant rollback (revert a commit), and identical, repeatable promotion from DEV to TEST to PROD.

4. The genuinely hard part: object IDs

Inside Morpheus, things refer to each other by numbers. A blueprint might say cloudId: 3. The catch: "cloud number 3" in DEV is a totally different machine than "cloud number 3" in PROD. If you blindly copy the file, you deploy to the wrong place.

The fix is a two-step translation:

On EXPORT (Morpheus → Git)

Replace the meaningless number with a human name.

cloudId: 3
      ↓
cloudName: "DEV-Nutanix"

On IMPORT (Git → Morpheus)

A per-environment lookup file translates the name back to that environment's real number.

cloudName: "DEV-Nutanix"
      ↓  (reads mapping_test.yml)
cloudId: 1   # what it is in TEST

This makes the YAML files environment-agnostic — they describe what you want, not where it physically lives. Here is a real before/after from this project:

Raw from Morpheus (JSON)

"id": 1,
"owner": { "username": "admin" },
"dateCreated": "2024-01-15...",
"cloudId": 3,
"network": { "id": "network-17" },
"plan": { "id": 12 }

Stored in Git (YAML)

# id / owner / dates stripped
cloudName: DEV-Nutanix
network:
  name: DEV-VLAN-100
plan:
  id: 12
  _logical_name: plan-12

6. Every component explained

scripts/morpheus_client.py — the one phone line to Morpheus

Every other script talks to Morpheus through this one file instead of calling the network directly. It reads two values — MORPHEUS_URL and MORPHEUS_TOKEN — from your .env file. Crucially, it reads them lazily (only when a call is actually made), so the test suite can import it without any credentials. To switch between the fake Morpheus and a real one you change only the URL; no code changes anywhere.

scripts/export.py — the "pull" button

Fetches blueprints and workflows from Morpheus and writes them as YAML files. While doing so it:

  1. Strips environment-specific fields: id, owner, dateCreated, lastUpdated, resourcePermission.
  2. Replaces cloudId: 3 with cloudName: "DEV-Nutanix" (looked up live from Morpheus).
  3. Replaces network.id: "network-17" with network.name: "DEV-VLAN-100".
  4. Adds a _logical_name to plan references so the importer can resolve them later.

scripts/importer.py — the "push" button

The reverse of export. Reads the YAML files, then uses config/mapping_<env>.yml to translate logical names back into that environment's real IDs. It uses upsert logic: if a blueprint of that name already exists it updates it, otherwise it creates it — so running it twice is safe (idempotent). If a name is missing from the mapping file, it stops with a clear error instead of pushing bad data. The --dry-run flag shows exactly what would happen and changes nothing.

scripts/drift_detect.py — the "did someone cheat?" checker

Answers: "Did someone change Morpheus directly in the GUI, bypassing Git?" It re-exports the live state, normalises it the same way as export.py, and diffs it against the YAML in Git. If anything differs it prints the difference and exits with code 1 — that non-zero exit is what fails the CI job and triggers an alert.

config/mapping_<env>.yml — the translation tables

One file per environment, mapping human names to that environment's real numbers. Example from mapping_dev.yml:

environment: dev
clouds:
  DEV-Nutanix: 3
networks:
  DEV-VLAN-100: 17
plans:
  plan-12: 12

The same logical name (DEV-Nutanix) points to 3 in mapping_dev.yml but to 1 in mapping_test.yml. That is the whole portability trick. Until real API access exists, these hold placeholder values.

tests/ — proof the logic is correct

26 automated tests that run with no network and no mock server. They check the stripping logic, the ID-to-name replacement, the reverse re-mapping, and the mock server's endpoints.

7. The mock server — why it exists and why it matters

mock_server/app.py is a small Flask web application that pretends to be Morpheus. It serves the realistic sample data in samples/ at the exact same URL paths the real Morpheus uses (/api/blueprints, /api/task-sets, /api/zones, /api/networks) and supports create/update/delete in memory for the duration of a session. It accepts any non-empty Bearer token.

This is the answer to "we don't have API keys" The scripts cannot tell the mock apart from the real thing — same endpoints, same response shapes. So the full lifecycle (export → import → drift) can be developed, tested, and demonstrated with zero credentials. Switching to a real Morpheus later is a one-line change in .env. This is a deliberate engineering choice (dependency inversion / contract testing), not a workaround.

8. The CI/CD pipeline (the robot)

.github/workflows/pipeline.yml defines what runs automatically:

push to ANY branch
   └─> [ validate ]  lint all YAML + run the 26 tests

push to `test` branch
   └─> [ deploy ]    dry-run import to TEST, then real import to TEST

manual trigger (workflow_dispatch)
   └─> [ promote ]   dry-run import to PROD, then real import to PROD  (gated)

daily at 06:00 UTC (schedule)
   └─> [ drift ]     export live state, diff against Git, fail if drift

PROD promotion only runs on a manual trigger and is tied to a protected GitHub "production" environment, so a human must approve it. Real Morpheus URLs and tokens would live in GitHub Secrets — never in the code.

10. Rollback (scripts/rollback.sh)

If an import made things worse, this script reverts by re-importing the configuration from the previous Git commit. It does this safely using a temporary Git worktree at HEAD~1, runs the importer from that snapshot, then cleans up. Usage: 

./scripts/rollback.sh --env test

It also reminds you to properly revert the bad commit in Git afterwards (git revert HEAD).

11. One-time setup

Good news On this machine the setup is already done: the virtual environment (.venv/), the dependencies, and the .env file (pointing at the mock) all exist. The steps below are only needed on a fresh machine. 
# From the project folder
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt

# Create the credentials file pointing at the local fake Morpheus
# .env contents:
#   MORPHEUS_URL=http://localhost:5000
#   MORPHEUS_TOKEN=mock-token-dev
#   MORPHEUS_ENV=dev
Shell note (you use the fish shell) The classic source .venv/bin/activate is written for bash. In fish it would be source .venv/bin/activate.fish. The simplest path is to skip activation entirely and call .venv/bin/python directly — that is what every command below does.

12. How to use it (day-to-day)

You work with two terminals. Terminal 1 runs the fake Morpheus and stays open. Terminal 2 is where you run commands.

Terminal 1 Start the fake Morpheus (leave it running):

cd /home/s1l3ntb1t/Documents/AtlasMorpheusProject
.venv/bin/python mock_server/app.py

Terminal 2 Typical workflow:

# Pull current state out of Morpheus into Git
.venv/bin/python scripts/export.py --env dev

# (edit the YAML files under environments/dev/ as needed)

# Preview the push — changes nothing
.venv/bin/python scripts/importer.py --env dev --dry-run

# Actually push
.venv/bin/python scripts/importer.py --env dev

# Check nobody changed Morpheus behind Git's back
.venv/bin/python scripts/drift_detect.py --env dev

13. How to test it (full walkthrough)

This proves every part works. Keep Terminal 1 (the mock) running for steps 1–5.

1Confirm the fake Morpheus is alive 
curl -s http://localhost:5000/api/ping
Expect: {"msg": "Morpheus mock server is running", "success": true}
2Export, then look at what came out 
.venv/bin/python scripts/export.py --env dev
cat environments/dev/blueprints/ubuntu-web-server.yml
Notice cloudId: 3 became cloudName: DEV-Nutanix, and the id/owner/date fields are gone. That is the portability transformation.
3Import — preview first, then for real 
.venv/bin/python scripts/importer.py --env dev --dry-run
.venv/bin/python scripts/importer.py --env dev
Dry-run prints [dry-run] would update: nginx-lb (and similar). The real run prints updated: nginx-lb.
4Drift detection — make it catch a "GUI change" 
# Simulate someone editing Morpheus directly, bypassing Git:
curl -s -X PUT http://localhost:5000/api/blueprints/2 \
  -H "Authorization: Bearer mock-token-dev" \
  -H "Content-Type: application/json" \
  -d '{"blueprint": {"id": 2, "name": "nginx-lb", "description": "CHANGED IN GUI"}}'

# The checker should now report drift and exit with code 1:
.venv/bin/python scripts/drift_detect.py --env dev

# Fix it (Git wins): re-import, then confirm drift is gone:
.venv/bin/python scripts/importer.py --env dev --type blueprints
.venv/bin/python scripts/drift_detect.py --env dev
First run prints DRIFT DETECTED; after the re-import it prints No drift detected.
5Run the automated test suite (does not need the mock running) 
.venv/bin/python -m pytest tests/ -v
Expect: 26 passed.
6When finished In Terminal 1, press Ctrl+C to stop the fake Morpheus.
Expected result All six steps pass. That demonstrates the complete GitOps lifecycle — export, version, import, drift detection, and an automated test suite — with no real credentials.

15. Switching to a real Morpheus later

If real access ever arrives, the only change is the .env file:

MORPHEUS_URL=https://your-real-morpheus-instance.com
MORPHEUS_TOKEN=your-real-api-token
MORPHEUS_ENV=dev

Then fill the real numbers into config/mapping_dev.yml (found by calling the real /api/zones and /api/networks). No script changes. That is the payoff of routing everything through one client.

17. FAQ

Do we need real Morpheus API keys to finish this project?

No. The project is mock-first by design. The full pipeline runs and is demonstrable on the local fake Morpheus with no credentials. API keys are only needed if you later want to point it at a real production system.

Isn't the mock server "just an API" too?

Yes — and that is the point. The whole project's job is to bridge Git and a REST API. The mock implements that same API contract locally so the bridge can be exercised fully. Removing the API entirely would defeat the purpose of the project.

What's the difference between export and import?

Export = Morpheus → Git (pull current state out, strip/translate IDs). Import = Git → Morpheus (translate names back to IDs, create or update).

What does "drift" mean?

Someone changed Morpheus directly through its dashboard instead of through Git. Git no longer matches reality. Drift detection finds that and fails the pipeline so the team is alerted.

Why strip id, owner, and dates on export?

They are specific to one environment/instant and would be wrong or meaningless in another environment. The files must describe what you want, not one system's bookkeeping.
