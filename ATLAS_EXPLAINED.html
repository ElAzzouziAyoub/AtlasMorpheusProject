ATLAS, explained from the ground up

What the samples/ folder is, what morpheus_client.py does, and exactly what happens — step by step — when you run the exporter and the importer.

The big picture in one sentence: ATLAS copies infrastructure definitions out of Morpheus into plain Git files (export), and pushes those files back into Morpheus (import) — and the samples/ folder lets you do all of this with a fake Morpheus so you never need real credentials.

1. The samples/ folder — a fake Morpheus

The real Morpheus is a big server with a REST API. You'd normally need a URL, an account, and an API token to talk to it. ATLAS is mock-first: instead of a real server, a small Flask app (mock_server/app.py) pretends to be Morpheus by reading these four JSON files and serving them at the exact same API addresses the real Morpheus uses.

Analogy: samples/ is a stunt double for the real Morpheus server. It says the same lines and stands in the same places, so you can rehearse the whole movie (export → Git → import) without putting the real actor at risk — or needing their phone number.
FileWhat's insideServed by the mock at
clouds_list.json3 "clouds" (data centers): DEV-Nutanix (id 3), TEST-VMware (id 7), PROD-VMware (id 12)/api/zones
networks_list.json3 networks: DEV-VLAN-100 (id 17), TEST-VLAN-200 (id 23), PROD-VLAN-300 (id 31)/api/networks
blueprints_list.json2 server templates: ubuntu-web-server (id 1), nginx-lb (id 2)/api/blueprints
workflows_list.json2 task sets: provision-web-server (id 5), decommission-cleanup (id 6)/api/task-sets

A blueprint is a recipe for a machine ("an Ubuntu box, on this cloud, on this network, this size"). A workflow is a list of scripts to run on that machine (install nginx, configure firewall…). Clouds and networks are the infrastructure the blueprint points at — ATLAS only reads those, never changes them.

Subtle but important: the mock keeps an in-memory copy of the data (_store in app.py). So while the server is running, a create or update really does change what the next request sees — that's why import actually "works". But restart the server and it reloads the pristine JSON files. The files on disk are never modified.

2. morpheus_client.py — the single phone line

Every script (export.py, importer.py, drift_detect.py) needs to talk to Morpheus. None of them call the network directly. They all go through this one module. That's the whole trick behind mock-first.

Analogy: it's a universal phone line. The scripts don't know or care whether the call is going to the real Morpheus or the stunt double — they just say "list the blueprints." You change who answers by swapping one setting; the scripts never change.

How it decides who to call

MORPHEUS_URL   = http://localhost:5000     # → the mock
MORPHEUS_URL   = https://morpheus.company.com   # → the real thing
MORPHEUS_TOKEN = anything-non-empty        # mock accepts any Bearer token

Both are read from the .env file at the project root (load_dotenv, top of the file). If either is missing it raises a clear error instead of failing mysteriously.

One detail worth knowing: list_blueprints and list_workflows auto-handle pagination. Morpheus returns results in pages of 100; these functions loop, bumping offset, until they've collected everything. The rest of the code just gets one clean list.

3. The Exporter — Morpheus ➜ Git, step by step

scripts/export.py  ·  run as python scripts/export.py --env dev

Its goal: pull the live blueprints out and write them as portable YAML — portable meaning environment-specific ID numbers are swapped for stable logical names, so the same file can later be pushed to dev, test, or prod.

  1. Read the arguments. --env (dev/test/prod) decides which folder to write into; --type can narrow to just blueprints or workflows.
  2. Build the cloud lookup. Calls client.list_clouds() and builds {3: "DEV-Nutanix", 7: "TEST-VMware", 12: "PROD-VMware"} — a number→name dictionary.
  3. Build the network lookup. Same idea: {"network-17": "DEV-VLAN-100", …}.
  4. Fetch every blueprint via client.list_blueprints().
  5. Strip the environment junk. Top-level fields that mean nothing in another environment are removed: id, owner, dateCreated, lastUpdated, resourcePermission.
  6. Translate IDs to names by walking config → tiers → instances: cloudId: 3 becomes cloudName: DEV-Nutanix; network id: network-17 becomes name: DEV-VLAN-100; the plan gets a _logical_name: plan-12 tag.
  7. Write the YAML to environments/dev/blueprints/<name>.yml.
  8. Do workflows too (lighter: just strip id/dateCreated/lastUpdated and write).

4. The Importer — Git ➜ Morpheus, step by step

scripts/importer.py  ·  run as python scripts/importer.py --env prod --dry-run

Its goal is the exact mirror of export: read the portable YAML, turn the logical names back into the real ID numbers for the target environment, then create or update each object in Morpheus.

  1. Read the arguments. --env picks the target; --dry-run means "show me what would happen, change nothing."
  2. Load the translation table for that environment: config/mapping_<env>.yml. This file says, e.g., in prod DEV-Nutanix → 1, while in dev it's → 3.
  3. Read each YAML file from environments/<env>/blueprints/.
  4. Translate names back to IDs (_remap_blueprint): cloudName: DEV-Nutanix → look up in mapping → cloudId: 1; network name → network-<id>; plan logical name → real plan id.
  5. Hard stop on a missing entry. If a name isn't in the mapping file, it raises "Cloud 'DEV-Nutanix' not found in mapping for env 'prod'" and skips that file — deliberately, so nothing ever gets built on the wrong cloud silently.
  6. Decide create vs update (upsert). It lists what already exists in Morpheus by name. Name already there → update (PUT). New name → create (POST).
  7. Dry-run or do it. With --dry-run it only prints would create / would update. Without it, it actually calls the API.
  8. Repeat for workflows, then print a summary like {created: 1, updated: 1, errors: 0}.
Why two mirror halves? Export is "translate to a language everyone speaks" (logical names). Import is "translate into the local dialect" (this environment's ID numbers). The Git file in the middle is environment-agnostic, which is what lets you promote dev → test → prod with the same file and just a different mapping.
